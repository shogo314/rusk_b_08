# β08のジェネリックextern試作

[棚卸し](beta08-inventory.md)のG1・G2について、外部ジェネリック型と関数を型検査・HIR/LIR・C++生成・実行まで通す最小実装を加えた。これは段階2の試作であり、ライブラリ移行の完了やextern基盤の完成を意味しない。以下の構文と参照記法は暫定案である。

## 宣言と共有ABI

```rusk
extern type<T> Cell {
    cpp_name: "std::shared_ptr<{T}>",
}
extern fn cell<T>(x:T)->Cell<T> {
    code: "Obj<@{Cell<T>}> @{fn}(Obj<@{T}> x,Loc){return make_obj<@{Cell<T>}>(std::make_shared<@{T}>(*x));}",
}
extern fn get<T>(x:Cell<T>)->T {
    code: "Obj<@{T}> @{fn}(Obj<@{Cell<T>}> x,Loc){return make_obj<@{T}>(**x);}",
}
let c:=cell(3);
wt get(c),get(cell("hello"));
```

出力は`3 hello`。型引数は通常の関数と同様に引数から推論でき、`cell::<Int>(3)`のように明示もできる。具体的なオーバーロードを優先し、明示した型引数はジェネリック候補を選ぶ。候補の重複検査、型の照合、具体化キャッシュはRusk関数と共通にした。

型注釈・返却先・引数の文脈から分かる期待型も、型引数の推論に使う。例えば`empty<T>()->Cell<T>`を宣言すれば、`let c:Cell<Int>:=empty();`で`T=Int`と決まる。`let c:Cell<Cell<Int>>:=cell(empty());`のように期待型を引数の呼び出しへ伝えることもできる。これは通常のRuskジェネリック関数とメソッド形式の呼び出しにも共通の規則である。

実引数・明示型引数・期待型は一致する必要がある。期待型で明示型引数を上書きしない。期待型は未確定の型引数を補うために使い、すでに型引数が決まった候補同士を戻り型だけで選び分けることはしない。期待型がなく型変数が決まらない`empty()`はエラーとなる。後続の文や未評価の後続引数まで戻って推論する仕組みは追加していない。

型パラメータは`extern type<T> Cell`の位置で束縛する。既存の`extern type Iter<Int> { ... }`は具体型の宣言のまま扱う。`extern type Cell<T>`を新旧両方の意味にすると、`T`が既存の型か型変数かによって宣言の意味が変わるため、試作では位置を分けた。ジェネリック関数は`extern fn name<T>`で宣言する。

`{T}`は具体化したRusk型の**C++本体型**を表す。例えば`{Int}`は`std::int64_t`であり、`Obj<std::int64_t>`ではない。引数・返却値の共有ABIに必要な`Obj<...>`は本体に明記する。`Unit`返却の関数はC++では`void`となる。通常のexternと同様に末尾の引数として`Loc`を受け取る。

この例の`Cell<Int>`の本体型は`std::shared_ptr<std::int64_t>`、引数のABI型は`Obj<std::shared_ptr<std::int64_t>>`となる。内側のポインタはこの外部型の意味の一部で、処理系が削除したり共有ラッパーと同一視したりしない。

同じC++本体型を持つ別名のRusk型は別の型として照合する。`First<Int>`と`Second<Int>`のC++表現が同じでも、互いの引数として渡せない。外部型は現時点では不透明型としてIRに保持する。

## 宣言の重複と順序

型コンストラクタは、その名前の系列全体を所有する。`extern type<T> Cell`と`extern type Cell<Int>`を併記して、一部の具体化だけを別定義にすることはできない。Ruskの`struct Cell<T>`・`enum Cell<T>`と具体的なextern型の組み合わせも同様に拒否する。宣言順を逆にしても拒否し、前の宣言位置を診断に含める。

テンプレートを持たない従来の具体型宣言は維持する。例えば`extern type Legacy<Int>`と`extern type Legacy<Str>`は異なる具体型として併記できる。ただし同じ具体型の二重宣言や、裸の型名`Legacy`との併記は拒否する。

外部型の型参照は、型・関数の宣言を登録した後で具体化する。後に宣言した外部型やRusk構造体を参照でき、入れ子の型参照も解決する。循環する展開は拒否する。これはRusk型の参照に関する規則であり、任意のC++断片の依存関係を解析して並べ替える機能ではない。

## C++参照の展開規則

| 場所 | 記法 | 意味 |
|---|---|---|
| 外部ジェネリック型の`cpp_name` | `{Int}`、`{T}`、`{Cell<T>}` | 検査・具体化した型のC++本体型 |
| 外部ジェネリック関数の`code` | `@{Int}`、`@{T}`、`@{Cell<T>}` | 同じ本体型。通常のC++の波括弧と区別する |
| 同じ`code` | `@{fn}` | この具体化に割り当てたC++関数名 |
| 同じ`code` | `@{call copy(T)->T}` | 通常の名前解決で選んだ関数・操作のC++名 |
| 同じ`code` | `@{invoke F(T)->R}` | 関数値Fの型を検査した呼び出し先。捕捉環境を第一引数に渡す |
| 同じ`code` | `@{return R}` | 返却ABI型。Unitなら`void`、それ以外は`Obj<本体型>` |
| 同じ`code` | `@@` | リテラルの`@`。`@@{T}`は展開後に`@{T}`となる |

関数名は処理系が割り当てるので、ジェネリックextern関数には`cpp_name`を指定しない。型引数の異なる具体化同士で関数本体が衝突せず、同じ具体化を再利用する。生成名の綴りは公開ABIにはしない。

参照の中では型名と山括弧形式の型引数を使える。試作は空白やTupleの丸括弧略記を受け付けない。未定義の型、不正な参照、閉じていない参照、型引数の個数違い、再帰する外部型の展開はRusk側でエラーにする。参照によって型を具体化したときに補助関数が増えても、呼び出し先の関数IDがずれないよう登録を行う。

これは明示したマーカーだけを展開するテンプレートであり、C++字句解析ではない。`T`という単語や`{Int}`をC++本体から一律に置換しない。通常のコメント・文字列・raw文字列・初期化子はそのまま残る。ただし`@{...}`はコメントや文字列の中でも展開するため、その記法自体を残す場合は`@@{...}`と書く。既存の具体的なextern宣言にはこの展開を適用しない。

## 関数・操作の参照

```rusk
extern fn detached<T>(x:T)->T {
    code: "Obj<@{T}> @{fn}(Obj<@{T}> x,Loc loc){return @{call copy(T)->T}(x,loc);}",
}
let x:=[1,2];
let y:=detached(x);
y[0]=9;
wt x,y;
```

出力は`1 2 9 2`。参照は`call 名前(引数型,...)->返却型`の形で、型を具体化した後、通常の具体関数・Ruskジェネリック関数・外部ジェネリック関数の候補から選ぶ。明示型引数は`@{call echo::<T>(T)->T}`と書ける。通常の具体的なオーバーロードを優先する規則と、曖昧な候補の拒否は共通である。指定した返却型と選んだ宣言が一致しない場合もエラーにする。

この参照は関数名だけを展開する。引数の式と末尾の`Loc`はC++本体に明記する。参照先がRusk関数なら推論された借用ABIの宣言と一致させ、外部関数なら通常の所有付きABIを使う。関数参照によってextern本体の効果が安全と証明されるわけではなく、外側のexternは引き続き未知として解析する。

具体化の登録を本体展開より先に行い、依存する外部関数を本体より前に宣言する。同じ型での自己参照やextern同士の相互再帰を扱い、型を無限に増やす展開には関数の具体化上限を適用する。別のC++関数を参照する場合、現時点ではその`cpp_name`が単純な識別子である必要がある。名前空間やC++テンプレートの特殊化を含む名前の前方宣言は未対応である。

この仕組みで参照できるのは、通常の候補解決に登録された関数である。コンパイラの専用経路だけで実装している構築・高階操作が自動的に参照可能になるわけではない。捕捉環境を持つ関数値には、次の専用の型付き参照を使う。

## 捕捉を持つコールバック

```rusk
extern fn apply<F,T,R>(f:F,x:T)->R {
    code: "@{return R} @{fn}(Obj<@{F}> f,Obj<@{T}> x,Loc loc){return @{invoke F(T)->R}(f,x,loc);}",
}
let total:=1;
let add:=(n:Int)=>(total+=n);
wt apply(add,2),total,apply((n:Int)=>"ok",1);
```

出力は`3 3 ok`。`invoke F(T)->R`はFが静的に分かる関数値であることと、その引数・返却型を要求する。この明示した参照を宣言の型要件として保持し、既存の関数値の型情報と照合する。型引数Rはコールバックの返却型から推論できる。コールバックを先に引数として渡せば、例えば`apply((xs:Vec<Int>)=>xs.len(),[])`の空配列にも型を伝えられる。

`invoke`の展開結果は呼び出し先の関数名であり、捕捉環境f、実引数x、LocはC++本体に明記する。型だけから捕捉値を作ったり、コンパイル時の値を埋め込んだりしない。同じ環境を共有した関数値と、`copy`で捕捉値を分離した関数値を、同じ具体化済みのexternへ渡せる。名前付きの具体関数も、従来の関数値への変換を通して渡せる。

`@{return R}`を使うと、RがUnitの場合も同じ宣言で扱える。C++では`void`を返す関数から`return callback(...);`と書けるため、値を返す場合とUnitの場合を分岐せずに表せる。このマーカーは返却型用であり、Unit型の引数の表現を変更するものではない。

関数値から別の関数値を返す場合も、それぞれの型情報から型引数を補える。型引数が増えなくなるまで照合を繰り返すので、参照マーカーの記述順には依存しない。これは明示した`invoke`参照による型の要件であり、任意のC++本体やRusk関数本体から一般の型要件を推論する機能ではない。文字列等に参照記法そのものを残す場合は、従来どおり`@@{...}`でエスケープする。

関数値の捕捉環境の所有・コピーには既存の仕組みを使う。[外部型に関数値を保持する例](https://github.com/shogo314/rusk_b_08/blob/main/examples/beta08/extern_callback_lifetime.rusk)では、ブロック内の文字列の要素を捕捉し、外側で関数値を取得・コピー・呼び出す。元の文字列の共有先の寿命を維持し、コピーした捕捉値は分離する。

型と呼び出し先が分かっても、externが関数値を何回呼ぶか・保持するか・別の共有を作るかは未確定である。そのためextern全体の効果は引き続き未知として扱う。readonlyやnoescapeで制限した値を捕捉する場合も、externへ渡すことで制限を消せない。コールバック内での実行時エラーは、通常のRuskの位置情報を保持する。

## 宣言の信頼元

標準ライブラリ・利用者ソース・処理系の生成物を、読込時の由来として区別する。表示用のファイル名では判定しない。この由来を関数宣言とジェネリック関数の具体化へ保持し、ネイティブ効果契約と直接生成の可否に使う。

標準ライブラリのジェネリックexternでは`effects`を指定でき、具体化した署名で既存の契約検証を通す。利用者のexternでは指定を拒否する。`<stdlib/core.rusk>`という表示名を与えても利用者宣言に権限は付かず、標準ライブラリの表示名を変更しても契約の意味は変わらない。由来を変更するソース構文やexternプロパティは提供しない。

この変更は信頼元の伝播を共通化するもので、任意のC++本体の検証や、コールバックの効果を契約に合成する機能ではない。型・保持・呼び出しに関する意味情報と、個別の直接生成の宣言化は引き続き移行対象である。

## 未使用宣言の検査

外部ジェネリック型と関数について、未使用でも署名・型参照の型名と型引数の個数、マーカーと呼び出し参照の構文を検査する。型・enum等の宣言をすべて登録した後に行うので、前方参照も使える。型変数には仮のInt等を割り当てず、型変数のまま検査する。

`copy(T)`が実際に使えるか、具体的なオーバーロードが一意か、外部型の展開が循環するかは、型引数の確定後に検査する。未使用の参照先関数名の解決や任意のC++本体の正しさまで確認するものではない。参照内の型の入れ子は64段までとしている。

既存のVec・Iter・Dict・Set・Tupleは、まだ通常のジェネリック宣言へ移していないため、検査でも現在の型コンストラクタの個数規則を使う。これは移行までの情報であり、ライブラリ名による恒久的な例外にはしない。外部ジェネリック型・Ruskの構造体・enumは、登録した宣言の型パラメータから個数を検査する。

## 試作の範囲と次の仕事

利用者定義の外部型・関数を、特定のライブラリ名の分岐を追加せずに動かすところを対象とする。外部関数の効果は未知として解析し、標準ライブラリの信頼契約を付けることはできない。引数のbinding/access/escape修飾も従来のexternと同様に拒否する。任意のC++本体とRusk署名の一致は、C++コンパイル時にも確認する必要がある。

次の項目はまだ未実装・未確定である。

- 宣言・具体化・関数参照の診断の整備と、標準操作の通常宣言への移行。
- コールバックの型要件と効果契約・保持情報を、信頼元を区別して接続する仕組み。
- 宣言に付随する型表現・共有先の情報、信頼元・効果契約・直接生成との接続。
- 型・補助定義の依存順序と、複雑なC++名を持つ関数の参照・前方宣言。
- Vec等の既存ライブラリの移行、自動copy等の導出方法。

試作の回帰テストは`tests/extern_generics.rs`。Int・Str・Boolでの具体化、共有と変更、通常版と最適化無効版、HIR/LIRへの接続、既存のオーバーロード、C++文字列の保存、異なる論理型の拒否、不正な宣言・参照を確認する。処理系変更前の比較元は`/tmp/rusk-beta08-pre-extern-baseline/`に実行ファイル・開始コミットのソース・環境情報を保存した。この一時保存先は公開成果物ではなく、後の性能比較用である。
